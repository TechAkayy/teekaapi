# Agent skills

Canonical skills and supporting resources live under `plugins/vibe` and `plugins/addy`. Each package has an [Agent Plugins standard](https://agent-plugins.org/) root `plugin.json`. Repository-root `.agents/skills/<name>` symlinks point directly to these canonical skill folders; Codex reads that folder. `.claude/skills/<name>` holds the same links for Claude. The links use relative targets so they work in another checkout, and both folders point at one source.

Start a skill by typing its name. In Codex, open a new task in this repository and type `$name`, for example `$lets-vibe`, `$progress-report` or `$api-and-interface-design`. In Claude, type `/name` at the start of the message, for example `/lets-vibe`. This README writes skill names in the Codex form; the Claude form of each is the same name after `/`. No marketplace registration, plugin installation, version suffix or cache refresh is required for this local setup. An existing task or session may have already loaded earlier instructions; use a new one after changing skills to verify discovery and use the current instructions.

All linked skills are explicit-only in both hosts; [the reason](#why-a-skill-starts-only-when-a-person-asks) is below. The [repository skill-selection rule](../../AGENTS.md#skills) defines when a user's slice request invokes Lets Vibe without naming the skill. The delivery, assessment, dependency-maintenance, peer-research and roadmap-review skills compose relevant Addy methods and session progress reporting after invocation. Canonical ownership remains with the `vibe` or the `addy` plugin; the standalone invocation names are unqualified and must be unique across both collections.

Use `$review-vibe` for independent assessment of existing work and `$test-vibe` for independent behavioral testing. Supply the work or version to assess and its relevant spec/task files or accepted instructions. Either may be requested before approval or after delivery; neither activates the other, implements fixes or closes a slice. For slice delivery, [Lets Vibe's assessment defaults and user overrides](plugins/vibe/skills/lets-vibe/SKILL.md#independent-assessments) govern assignment alongside primary implementation, verification and self-review. An assessment requested from its author uses one independent assessor; a separate assessor task performs the role directly.

The Addy collection is copied from its upstream source without body changes; see [source revision and integration metadata](plugins/addy/UPSTREAM.md). Discovery does not establish that every method's external tools are configured.

Use `$dependency-upgrade` for a selected dependency update, `$grill-peers` for a bounded peer-source investigation, and `$roadmap-review` for an evidence-backed roadmap proposal and guided decisions. Each uses its own procedure, relevant Addy methods and shared method selection with checkpoints determined by the active execution mode. They do not automatically start Lets Vibe delivery; peer findings and roadmap proposals do not themselves authorize implementation.

Use `$handoff` to pass current work to another session. It brings the owning records up to date, has one independent reviewer confirm that a cold reader can continue from them, and then gives a short prompt; it creates no handoff file and does not continue the work. In [a chain of slices](plugins/vibe/skills/lets-vibe/references/contract-core.md#a-chain-of-slices) that the user authorized, the session that closes a slice runs it for the next slice and then starts the new session; in orchestrated mode the orchestrator gives the word for it and starts the next pair. Use `$walkthrough` for a guided explanation of a subject the user chooses. It asks what to explain, then presents it in the conversation in Simplified Technical English with a small number of visuals, and changes nothing. Inside a Lets Vibe run, a plain request for a handoff or a walkthrough starts them; outside a run, type the name. Both use the shared [writing rules](plugins/vibe/skills/progress-report/references/simplified-technical-english.md), which also govern the progress report.

The shared [UI decision consultation gate](plugins/vibe/skills/lets-vibe/references/addy-method-gates.md#ui-decision-consultation) applies in every execution mode. Lets Vibe carries agreed designs and pending choices through delivery; Review Vibe checks their preservation alongside foundation reuse, ownership and lifecycle evidence.

## Why a skill starts only when a person asks

These skills are available to everybody and forced on nobody. An agent must not start a Vibe or Addy skill because a task looks like a match. A teammate who asks for a small fix gets that fix, not a method that the teammate did not choose.

A skill starts in one of two ways:

1. A person types its name: `/name` in Claude, `$name` in Codex. Each skill can be started this way.
2. Lets Vibe selects it. A person who starts Lets Vibe has chosen the full workflow. Inside that run, Lets Vibe selects the Addy methods that the work needs, and a request for a handoff or a walkthrough starts those skills, with no skill name.

Lets Vibe is the one skill that plain words can start: a request to start or continue a slice starts it. A slice is a unit of that workflow, so the person who asks for one has chosen that workflow.

Each host has its own setting for this rule. Codex: `allow_implicit_invocation: false` in the skill's `agents/openai.yaml`. Claude: `user-invocable-only` for the skill under `skillOverrides` in `.claude/settings.json`. When you add a skill, set both.

Do not make a skill start by itself to save typing. A person who wants that can set it in personal settings, which are not committed.

### The gate in Claude

- With `user-invocable-only`, a skill is in the `/` menu and is hidden from Claude's own list. Claude treats a skill that has no entry as available to start by itself, so each skill needs its entry; validation refuses a missing one.
- Lets Vibe reads the methods it selects by their file path, so it does not need Claude's list.
- For a personal override, set the skill under `skillOverrides` in `.claude/settings.local.json`. Claude applies that file over the committed one, and Git ignores it in this repository.
- Claude reads `AGENTS.md` directly from version 2.1.277. Do not add a `CLAUDE.md`, a `.claude/CLAUDE.md` or a `CLAUDE.local.md`: with one of them, Claude stops reading `AGENTS.md`. Validation refuses these files.
- A skills folder that did not exist when a session started is not seen by that session. Use a new session after the links are first created.

Source for the Claude behavior: the Claude Code documentation on [skills](https://code.claude.com/docs/en/skills), [settings](https://code.claude.com/docs/en/settings) and [AGENTS.md](https://code.claude.com/docs/en/memory#agents-md), read on 8 October 2026.

## Skill maintenance

Lets Vibe can resume agreed work or help define new scope, including after the roadmap is complete. Its [work-selection rules](plugins/vibe/skills/lets-vibe/SKILL.md#select-the-work) own that behavior.

1. Edit the canonical skill under `plugins/<owner>/skills/<name>/`. For Addy updates, follow [UPSTREAM.md](plugins/addy/UPSTREAM.md), preserving vanilla upstream bodies and the integration metadata that this package adds.
2. For an addition or rename, create the matching repository-root `.agents/skills/<name>` and `.claude/skills/<name>` relative symlinks to `../../tooling/agents/plugins/<owner>/skills/<name>`, set the skill to `user-invocable-only` under `skillOverrides` in `.claude/settings.json`, and set `allow_implicit_invocation: false` in its `agents/openai.yaml`. For a deletion or rename, remove its obsolete links and its settings entry. Content-only edits flow through existing links without copying or reinstalling.
3. Update affected `agents/openai.yaml` prompts, local resource links, method-routing references and invocation examples, including this catalogue. Search for the old name/path when renaming or removing a skill. Review package exports and manifests when their paths or package identity change. Keep skill names unique across the collections.
4. Run `pnpm --dir tooling/agents run validate` for skill, reference and metadata edits. Run affected agent tests when changing validation or progress tooling; select product build/integration checks when product behavior or those boundaries change. Use `pnpm --dir tooling/agents run check` when the accepted task requires the aggregate, rather than for every instruction-only edit. Review the diff, including new and removed symlinks, and verify discovery in a new Codex task and a new Claude session when the inventory or invocation metadata changes. Structural validation cannot verify that method routing still makes sense or that the host has refreshed its inventory.

## Local validation

From the repository root, `pnpm --dir tooling/agents run validate` checks plugin schema identifiers, matching folder names and non-empty versions, skill frontmatter, explicit-only invocation metadata and local Markdown file targets. It also checks that every direct skill has exactly its matching relative discovery link in both host folders, that links are not stale or misdirected, and that default prompts name their own skill. For Claude it checks that each skill is `user-invocable-only` in `.claude/settings.json`, that no settings entry is left for a removed skill, and that no `CLAUDE.md` file hides `AGENTS.md`. It also checks the [record rules](../../AGENTS.md#records) on every file that Git tracks or that is new and not ignored: it refuses a commit or a branch of this repository, and a phase or slice number outside `plans/`, in the content of each text file and in the path of each file. The form of a phase or slice number is the project's own. [records.json](records.json) gives it in `sliceId` as a regular expression, for example `"S[0-9]{2}(?:\\.[0-9]{1,2})?"` for the letter S, two digits and an optional sub-slice number after a point; a number counts only where no letter or digit touches it. While `sliceId` is null, the numbers are not checked. Git decides what is a commit or a branch of this repository, so an outside pin and a content digest pass with no list of permitted strings. Only a branch name that holds a `/` is checked, which is how the lines of this repository are named; a name with no `/` cannot be told from an ordinary word or a package name. Dependency lock files, binary files and the paths in [plans/record-rules-exempt.txt](../../plans/record-rules-exempt.txt) are not read, and an entry of that list that matches no file is refused. Without Git the check fails. It cannot check that a behavior is proven by a test. It recursively discovers `SKILL.md` files under each standard `skills/` directory and parses YAML and Markdown, including shared references, without running skill scripts or changing plugin content. It does not validate the complete plugin schema or check external URLs, Markdown anchors, upstream identity, live Codex or Claude discovery, or behavioral compliance.

`pnpm --dir tooling/agents run check` also runs focused validator and progress tests against temporary synthetic files. It does not check the saved progress report, because a repository has none before its first slice starts; add the `--check` command below to your own aggregate check and CI job from then on. Validation tooling and its parser dependencies are development-only; the plugins remain the package's declared distribution content. Use the root toolchain and installation instructions in [README.md](../../README.md).

The metadata compatibility check follows the recognized field types in Codex source revision `6ae8dcf6e10ebe85ba62d6ceb1cc8b5ca87a5628`: `codex-rs/skills/src/parser.rs`, `codex-rs/ext/skills/src/loader/metadata.rs`, `codex-rs/skills/src/interface.rs` and `codex-rs/protocol/src/protocol.rs`. It checks skill names/descriptions and optional frontmatter `metadata`/`short-description` shapes so malformed metadata cannot prevent skill loading. It also checks interface fields, dependency tools/OAuth and policy products so malformed surrounding metadata cannot silently discard the explicit-only policy. Unknown extension fields remain allowed. This is a structural compatibility check, not a complete Codex schema or an execution test; reassess it when the loader contract changes.

Discovery conservatively checks all source skill files, including hidden directories and symlink targets, with cycle detection. It does not reproduce Codex's host-dependent hidden-directory rules or traversal limits, so the validated source inventory can be broader than the host inventory. Unreadable discovery targets fail validation rather than producing a successful incomplete scan.

## Run report

In each execution mode a [reporter](plugins/vibe/skills/lets-vibe/references/run-report.md) can follow a run from outside. The run report is printed and never saved:

```sh
pnpm --dir tooling/agents run run-report [--minutes <n>]
```

It reads the project pointer, the selected task document, the Git state and the session logs of the sessions in `execution.sessions`, and prints a fixed form: first one line that says if the run needs the user, then the progress line with only the branch of the task tree that is in work or on hold, the repository, what is owed to the user under the words “Owed to the user.” in the plan or the roadmap, and each conversation. The first line is “Nothing needs you.”, or the request of the session that speaks with the user when its last message begins with “Needs you:”, or the flags to check. The window is the last 60 minutes unless `--minutes` names another. It quotes and counts; it gives no reading of its own.

A session log is read by the `session` identifier in the pointer. The tool has a reader for the logs of Claude and of Codex and names no host; `CLAUDE_CONFIG_DIR` and `CODEX_HOME` move where it looks. A session finds its own identifier with `run-report --mark` and then `run-report --find <marker>`. [run-report.json](run-report.json) holds, for this repository, the patterns of the commands that the report lists as outside commands; a command that only reads is never listed.

## Saved progress report

The selected task document from `plans/project-state.json` owns report state; the pointer owns the current execution mode and its scope under the [project-pointer rules](plugins/vibe/skills/lets-vibe/references/requirements-alignment.md#project-pointer). Its sibling `progress.md` is generated, with the full report in native nested Markdown lists, as defined in the [delivery progress rules](plugins/vibe/skills/lets-vibe/references/progress.md#weighted-progress-and-presentation). Long prose wraps within its list item at the preview width. Direct invocations print the same saved Markdown in the conversation. Run these commands from the repository root with the declared toolchain:

```sh
pnpm --dir tooling/agents run progress
pnpm --dir tooling/agents run progress --write
pnpm --dir tooling/agents run progress --check
pnpm --dir tooling/agents run test:progress
```

Default mode renders to stdout. `--write` validates first, replaces changed generated output atomically and leaves identical files untouched. After a write it prints one line for each task or step whose status is not the one in the saved report, in the symbols of the report: for example `[x] D2 Owner review › T7 Join the requests — COMPLETE`, or `[!] D4 Recovery › T17 Recover the guest — BLOCKED: Waits for T23.` For this the report holds the status of each leaf in one hidden line; a first report, a report from before that line existed and a report whose hidden line was altered have nothing to compare with and print no status line. A placement that gets a new identifier counts as a new leaf, so its status is printed one time though it did not change. `--check` is read-only: missing, stale or altered output fails with a regeneration command. The two flags are mutually exclusive. Add `--root <workspace>` to select another local fixture; the default is this checkout, independent of the caller's current directory. Unknown arguments, malformed inputs, unrelated existing output and non-regular destinations (including symlinks) fail explicitly. Neither mode edits task state, approvals or Git.

**In Claude, a hook writes the report again.** The committed `.claude/settings.json` holds one hook that Claude starts after each edit of a file with its edit tools. The hook runs `tooling/progress-hook.ts`, which does nothing unless the edited file is the task list that the pointer selects. For that file it runs the write command. When a status changed, the agent gets the printed status lines as context, to give to the user. When the task list is not valid, the agent gets the refusal and the saved report stays as it was. Limits: an edit through a shell command or by another program does not start the hook; Codex has no such hook; in both cases run the write command. The hook uses the Node on the path of the session. With a Node older than the declared range the hook fails after each edit of each file, not only of the task list, because that Node cannot start the script; use the declared Node. For everybody the cost is one start of Node for each edit, about 55 milliseconds. Claude gives the hook the root of the project where the session started: a session that was started in another checkout and edits this task list does not write this report. Validation does not check the hook. Source for the hook behavior: the Claude Code documentation on [hooks](https://code.claude.com/docs/en/hooks), read on 8 October 2026.

Maintain exactly one `vibe-progress` fenced YAML block in the selected task Markdown. Its fields are `unit` (matching the pointer), `current`, `next`, nonempty lists `completed`, `remaining`, `blockers`, `verification`, `candidate`, and eleven ordered `steps`. Each step has its accepted numeric `id`, full `name`, integer `weight`, `class` (`supporting` or `substantive`) and either a leaf `status` or `children`. Deliverable children use ordered `D1`, `D2`, … identifiers, with inserted deliverables such as `D3A`, `D3B`, `D3C` following their base in suffix order. They retain their full names, weights and task children. Task placements have a unique `id`, a numeric `task` reference or an inserted task reference such as `27.1` or `D3A.1`, weight and leaf status; canonical titles come from `## Task N — Title` or `## Task 27.1 — Title` / `## Task D3A.1 — Title` headings. Decimal task IDs render as `T27.1`; deliverable-prefixed task IDs render unchanged. Zero-weight placements can show accepted prerequisites without changing the agreed allocation; they still participate in parent status and acceptance checks. Parent statuses derive from children, whose weights must sum to the parent. Supporting weight cannot exceed five percent of the total.

A task placement may have `children`: sub-task placements whose `task` references extend the parent's number, such as `5.1` under Task 5 and `5.1.2` under Task 5.1, each with its own `## Task 5.1 — Title` heading. Quote a decimal reference in the YAML (`task: '5.1'`), so that it stays text. Use them to divide a large task under the [task size rule](plugins/vibe/skills/lets-vibe/references/progress.md#task-size-and-breakdown). When every weight is 0, the report shows `percentage unavailable: weights are not agreed` in place of the bar; this is the form the plan step creates before the user agrees the weights. Below the headline the report names the leaves that are IN PROGRESS and the leaves on hold, when there are any. When more than 3 leaves are IN PROGRESS, the reader report adds one warning line that starts with `Check:`; it refuses nothing.

The renderer has one form of the report, the reader report. It does not read the status of the slice for the form, so the report does not change at the close. It prints the progress state and one line for each task to the third level, and it does not copy the action lines from the task sections: a task line shows a count such as `(1 of 3 actions done)`. The heading of a task is its one title; a `label` on a task placement is refused. The renderer applies the mechanical part of the [language and length rule](plugins/vibe/skills/lets-vibe/references/progress.md#language-and-length) to every text it prints: a maximum of 3 sentences in one item and 25 words in one sentence. It reports the item to correct and does not check the task body, which is written for agents. The renderer does not check word choice, voice or truth.

The reader report prints a task line to three levels of task numbers, for example `T2`, `T2.3` and `T2.3.4`; the task list keeps the full numbers at each depth. A line with lines below it — a step with deliverables, a deliverable, a divided task — has no status word and no reason of its own: its box shows `[x]` when each line below it is done, `[ ]` when none is started, and in each other case a count of its direct children that are done, such as `[2 of 6]`. A completed task shows its checked box and no word, so the words IN PROGRESS are only on a task in work. A task of the third level that is divided shows `[4 of 9 parts]`, where a part is a sub-task below it that is not divided again. Below that line the report names, by its title and with no number, each part in work and each part that is on hold, deferred or resolved with no implementation, with its status and its reason; a pending part and a completed part are not named. The two lines below the headline name a deeper leaf by its third-level task and its title, such as `T2.3.4 › Read the markers`. The weights and the percentage do not change. The reader report refuses a task deeper than three levels that is not placed below its third-level task.

The current report reads `execution.mode` (`supervised`, `copilot`, `autonomous` or `orchestrated`) and `execution.scope` from the pointer and displays the scope beside the mode. A task-limited scope must identify an existing canonical task in the selected slice. A changed mode or scope makes the saved report stale even when task content is unchanged. Historical task blocks may retain `mode`; it is used only when the pointer has no execution record, with supervised as the fallback when both are absent. Omit `mode` in maintained current task blocks to keep one source of selection. The renderer reports the recorded scope; the resuming agent must still check whether the requested work falls within it and whether it is unfinished.

Leaf treatments, required reasons, uppercase labels, checkbox handling, parent aggregation and weight rules are defined once in the [delivery progress treatment table](plugins/vibe/skills/lets-vibe/references/progress.md#plan-and-status). Use those structured status keys; do not encode treatments in canonical task titles. The legacy `held` key remains supported. Optional `bullets` add placement-specific details; action checklists come from owning task sections. Repeated placements retain separate completion and allocations. The validator checks status keys, required nonempty reasons, title-prefix duplication and actual-completion/checklist contradictions. It cannot establish that a reason is truthful or an approval exists; the agent and independent reviewer must check the evidence.

The generated source digest makes edits anywhere in the task document detectable, including supporting prose. It is only a freshness comparison, not an approval signature. A successful check establishes agreement with current maintained inputs at that instant; it cannot prove completion claims or detect work never recorded there. Use short linked conversation updates for automatic workflow reporting and regenerate from the source before checkpoints. Direct user invocations follow the [Progress Report presentation rules](plugins/vibe/skills/progress-report/SKILL.md#present-the-report). Do not hand-edit the generated view.
