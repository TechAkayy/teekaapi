# Grill Peers

Investigate one named peer and a bounded question or feature area. Establish the intended decision, inspected revision, relevant project scope, exclusions and sufficient evidence. A broad peer survey is valid when explicitly requested; do not silently expand a narrow question into a whole-repository review. Resolve ambiguous peer names from available repository context or ask the user.

## Evidence and write boundaries

Read applicable instructions and identify the peer's repository and exact revision. Use committed source at that revision when practical. If working changes are included, identify them explicitly and preserve a stable comparison; never label dirty evidence as committed truth. A moving or unknown input blocks conclusions that depend on its identity, not unrelated inspection. On resume, recover the inspected scope and next unanswered question rather than starting over.

Peer checkouts remain read-only. This invocation does not fetch into them, install dependencies, run their code, build outputs or create caches. If execution is needed to resolve an important uncertainty, explain the proposed probe and obtain authorization covering an isolated execution copy and its effects. Static inspection must not be reported as executed behavior.

Return findings in the session or update the agreed existing research document under the project's research location. For a new durable research output, establish its path within the accepted scope; use the current repository's plans/research convention. Preserve prior findings and explanations, marking verified changes rather than replacing history with a shorter summary. No separate retrospective format, companion HTML or registry is required. Evidence can recommend code reuse or roadmap work; it does not authorize either.

## Addy methods

Apply the [shared selection and supervised group checkpoints](../lets-vibe/references/addy-method-gates.md) using these research transitions. Do not enter the Lets Vibe delivery steps. Read selected skills/resources, announce purpose and outputs, and apply only activities within the research assignment.

- Before investigating, assess `spec` and apply `doubt-driven-development` to material assumptions. Use `source-driven-development` when an external framework or public contract needs version-specific official documentation, and `context-engineering` when the selected context needs organization.
- Before recording recommendations, assess `review`: use `code-review-and-quality` for implementation-quality claims, `api-and-interface-design` for boundary analysis, `security-and-hardening` for trust concerns and `documentation-and-adrs` for recording consequential decisions. These methods assess the peer; they do not authorize editing it.

Method selection and application are required; unavailable methods or tools must be disclosed with the resulting limits. Do not manufacture findings or run implementation activities to satisfy a method. An independent reviewer is optional and requires explicit selection.

## Investigate

Follow the [evidence-reading procedure](references/evidence-reading.md). Work through connected entry points, types, configuration, runtime behavior, tests and direct consumers. Record findings incrementally. Inspect failure, cancellation and cleanup where relevant, and challenge the strongest proposed conclusions before presenting them.

For each material finding distinguish peer fact, project fact, inference, recommendation and accepted decision. Cite repository, revision, path and relevant symbol or line. State whether to adopt, adapt, reimplement from a pattern, defer or reject, with benefit, trade-offs, dependencies, likely project owner, validation needs and unresolved uncertainty. Direct reuse requires a bounded source candidate with license and dependency evidence; it remains a recommendation until separately authorized.

## Progress and completion

Use [progress-report](../progress-report/SKILL.md) automatically under its supporting-work rules. Report the agreed question and revision, meaningful findings or changed conclusions, blockers and the final assessment. Keep session progress separate from durable research findings.

Finish when the agreed questions are answered to the stated evidence level or clearly blocked. Report inspected scope, evidence, non-adoption reasons, unexecuted probes and remaining uncertainties. Preserve applicable evidence for a later follow-up. Present the result for review under the active mode; do not automatically investigate another peer, change the roadmap, implement a candidate or commit research.
